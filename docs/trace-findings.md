# Arc-sweep-range bug — trace findings

Generated by Task 6 of the poly_bool_arcs sweep fix plan. Read by a human
before approving Phase 2 tasks.

## What the test expected

The minimal failing test (`test/arc_sweep_range_test.dart`, "union: rect-with-right-arc vs rect-overlapping-arc") unions two polygons: polygon A is a rectangle (0,0)-(100,100) whose right side is replaced by a clockwise semicircle centered at (100, 50) with radius 50 — the RIGHT half of that circle, bulging outward through (150, 50). Polygon B is a rectangle (120, 25)-(200, 75) overlapping A's arc region. The helper `expectArcSweepWithinInputs` asserts that every arc in the union result has both endpoints on the original input sweep, i.e. angles in `[-π/2, +π/2]` clockwise (the right half only). Coordinates use the y-down / screen convention that the test helper explicitly documents: `clockwise=true` means angle INCREASES in atan2 terms.

## What actually happened

The test fails with:

```
region 0 edge 1: arc end (50.0, 50.0) angle=3.141592653589793 is
outside every input sweep on circle center=(100.0, 50.0)
```

An arc endpoint at `(50, 50)` — the LEFT extreme of A's circle at atan2 angle π — appears in the output. That point lies on the LEFT half of the circle, the complement of the input sweep. Two different arcs in the output each use (50, 50) as an endpoint.

## First out-of-sweep emission point

**Location:** `lib/src/intersecter.dart`, method `_addArcSubSegments` (lines 126–195), the extreme-filtering loop at lines ~146–152 that calls `geo.angleInArcRange`.

**Evidence from trace** (`build/arc_trace.log`, lines 3–11):

```
[TRACE addArcSubSegments INPUT] pt1=(100.0, 0.0) pt2=(100.0, 100.0) center=(100.0, 50.0) r=50.0 cw=true
[TRACE addArcSubSegments ANGLES] startAngle=-1.5707963267948966 endAngle=1.5707963267948966 cw=true
[TRACE addArcSubSegments EXTREME] ext=(50.0, 50.0)  angle=3.141592653589793 inRange=true    <-- WRONG (left half)
[TRACE addArcSubSegments KEEP]    split=(50.0, 50.0) angle=3.141592653589793
[TRACE addArcSubSegments EXTREME] ext=(150.0, 50.0) angle=0.0               inRange=false   <-- WRONG (right half)
[TRACE addArcSubSegments EMIT]    start=(50.0, 50.0) end=(100.0, 0.0)   cw=false
[TRACE addArcSubSegments EMIT]    start=(50.0, 50.0) end=(100.0, 100.0) cw=true
```

The same pattern is observed in `build/arc_trace_outside.log` for the "arc fully outside" test, where B does not touch A at all — proving the out-of-sweep endpoints are introduced at INTAKE, not by any clipping logic. Downstream, all `_checkArc*Intersection` calls operate on the already-corrupted sub-arcs, and `[TRACE chainer EMIT]` faithfully copies them into the final `ArcVertex.arcToNext` values.

For the >π case (`build/arc_trace_long.log`), the same inversion fires: input start=0 end=π clockwise (a 270° sweep going through the TOP of the circle), and `angleInArcRange` rejects the top extreme (50,0) at +π/2 (`inRange=false`) while accepting the bottom extreme (50,-100) at -π/2 (`inRange=true`). This is the same bug manifesting on a different input.

## Why this happens (hypothesis)

There is a **coordinate-system-convention mismatch** between `ArcData.clockwise` and `Geometry.angleInArcRange`:

- The library's public contract (confirmed by the test helper at `test/helpers/arc_sweep_assertions.dart:125`) interprets `clockwise=true` in the **y-down / screen** convention — the visual screen direction — which, in terms of raw atan2 output (which is y-UP, math convention), means the atan2 angle **increases** along the sweep.
- `Geometry.angleInArcRange` (`lib/src/geometry.dart:40–49`) implements `clockwise` in the **y-up / math** convention: when `clockwise=true`, angles **decrease** from start to end.

These two conventions are exact opposites. The code therefore uniformly selects the complement of the intended sweep: for `(-π/2 → +π/2 clockwise)` the user means the right half via angle 0, the code accepts the left half via angle π. For `(0 → π clockwise)` the user means the long 270° arc through +π/2, the code accepts the short 90° arc through -π/2. Same sign flip every time.

## Proposed fix (for Phase 2 / Task 7)

**File:** `lib/src/geometry.dart`
**Method:** `angleInArcRange` (and correspondingly `filterToArcRange`, which already delegates to it correctly)
**Change:** Swap the `clockwise` branches so that `clockwise=true` accepts angles where the atan2 angle **increases** from `startAngle` to `endAngle` (with wrap-around), and `clockwise=false` accepts angles where it **decreases**. Concretely, swap the bodies of the two outer `if (clockwise) { ... } else { ... }` branches (lines 40–57). Equivalently, invert the `clockwise` parameter at the top of the method.

This aligns the library's internal angle math with the externally documented y-down convention of `ArcData.clockwise`. Because `_addArcSubSegments` and every `filterToArcRange` caller flow through `angleInArcRange`, fixing this one method corrects intake normalization, arc-line intersection filtering, and arc-arc intersection filtering in one change.

Prefer editing `angleInArcRange` itself (one site) over flipping the `clockwise` flag at each call site — fewer edits and keeps the Geometry helper consistent with its public naming.

**Verification path:** The existing `test/geometry_test.dart` should be reviewed first — if it currently encodes the math convention (tests passing against the BROKEN semantics), those tests must be updated in the same commit or they will keep the bug locked in. If they use the y-down convention, they will start passing alongside the sweep-range tests.

## Scope of the fix

**Single-site fix, multi-call-site verification.** The bug is one logical inversion in `angleInArcRange`. Evidence:

1. All out-of-sweep output in every failing test traces back through `_addArcSubSegments` to exactly this one helper (`build/arc_trace.log`, `build/arc_trace_outside.log`, `build/arc_trace_long.log`).
2. `filterToArcRange` (used by `lineArcIntersection` and `arcArcIntersection`) delegates to `angleInArcRange` — the same fix propagates automatically.
3. The chainer does NOT introduce out-of-sweep data; it only copies what the intersecter produced.
4. `rayArcIntersections` also calls `angleInArcRange` and will silently behave correctly again once fixed (point-in-polygon tests were likely giving inverted answers too).

However, the fix can destabilize `geometry_test.dart` if those tests currently lock in the inverted behavior. That file MUST be reviewed and, if needed, updated in the same Phase-2 commit.

## What about the "arc fully outside" failure?

**Same root cause, no second class.** `build/arc_trace_outside.log` shows identical TRACE output to the minimal case up through `[TRACE addArcSubSegments EMIT]`. Because polygons A and B do not interact, every `_checkArc*Intersection RESULT` returns an empty or trivial endpoint-only list; the corrupted (50,50) sub-arc endpoints flow straight from intake through the chainer into the output. This proves the bug is purely in arc intake/normalization, not in clipping. A single fix to `angleInArcRange` should clear both this test and the minimal failing case; no additional iteration rounds are anticipated for Task 8 on account of this edge case.

The >π-sweep case (`build/arc_trace_long.log`) is also the same bug, not a distinct y-extreme issue — the y-extreme machinery in `_addArcSubSegments` is logically correct, it is simply consulting an inverted membership predicate.
